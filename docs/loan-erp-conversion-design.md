> 작성일: 2026-08-19

## 1. 확정된 정책 (사장 결정)

| # | 항목 | 결정 |
|---|---|---|
| 1 | 이자 계산 | **혼합** — 정기 회차 스케줄은 월할(연이율÷12), 중도상환·기한이익상실 등 **정산 시점은 일할(365일)** 재계산 |
| 2 | 상환방식 | **계약별 선택** — 원리금균등 / 원금균등 / 만기일시(이자만 납입) |
| 3 | 연체 판정 | **D+1** — 납입예정일 다음날부터 즉시 연체 |
| 4 | 수납 충당순서 (일반) | **법적비용 → 이자 → 원금** |
| 4-1 | 수납 충당순서 (상각채권) | **법적비용 → 원금 → 이자** — 대손상각된 채권은 원금을 먼저 충당 |
| 5 | 최고이율 | **연 20% 상한 강제** (대부업법). 계약이율·연체이율 모두 검증 |
| 6 | 연체이자 부과 | **계약 등록 시 선택** (부과 / 부과하지 않음). 금소법상 개인고객 3천만원 이하 미부과 케이스 대응 |
| 7 | 부가세 | **전면 삭제**. 대부업 이자수익은 면세이므로 부가세 로직·세금계산서 발행을 제거 (매입 부가세 포함) |
| 9 | 이자수익 구분 | **영업수익(대출채권 이자) / 영업외수익(예금이자)** 계정 분리. 손익계산서에 영업이익 단계 신설 |
| 8 | 회계 인식 | **현금주의** 유지 (기존 렌터카 ERP 기준 승계) |
| 10 | 매입 부가세 | **제외** — 매출·매입 모두 삭제. 임차료·비품 등 매입 항목도 총액(공급대가)으로 비용 계상 |
| 11 | 법적비용 범위 | 변제충당 1순위에 **포함**. 법적절차 모듈이 기록한 신청비용·추가비용·확인비용 합계에서 환입을 뺀 금액 |
| 12 | 이자 단계 내부순서 | **지연배상금 우선** → 약정이자 |
| 13 | 렌터카 테넌트 | **폐기** (분리 유지 안 함) |
| 14 | 기한이익상실 | **신청식(수동 등록)** — 자동 트리거 없음 |

## 2. 채권 상태 5종

### 2.1 상태 정의

| 상태 | 성격 | 확정 방법 |
|---|---|---|
| **정상** | 미납 회차 없음 | 파생 (스케줄 실시간 판정) |
| **연체** | 납입예정일 경과 미납 회차 존재 | 파생 (스케줄 실시간 판정, D+1) |
| **해지** | 기한이익상실 등록됨 → 잔여원금 전액 즉시 청구 | **저장** (이벤트 등록 시 확정) |
| **상각** | 대손상각 등록됨 | **저장** (이벤트 등록 시 확정) |
| **종료** | 완제(원리금 전액 회수) 또는 만기 정상종료 | **저장** |

> 핵심 원칙: **해지·상각·종료는 이벤트 발생 시점에 `loan_contracts.status`에 저장하고, 정상·연체는 저장하지 않고 조회 시점에 미납 스케줄로 파생 판정한다.**
> 현재 코드는 `ContractQueryController.java:132-146`에서 저장상태와 파생상태가 뒤섞여 있어 이 구분을 명확히 재작성한다.

### 2.2 상태 전이

```
        ┌──────────────── 완납 ────────────────┐
        ▼                                      │
     [정상] ──── 납입일+1일 미납 ────▶ [연체] ──┘
        │                               │
        └──── 기한이익상실 등록 ────────┴──▶ [해지]
                                             │  (잔여원금 전액 청구 개시)
                                             │
              대손상각 등록 ─────────────────┴──▶ [상각]
                                                   │
        [정상]/[연체]/[해지] ── 완제 ──▶ [종료] ◀───┘ (상각채권 완제 시)
```

전이 규칙:
- **해지**는 기한이익상실 등록으로만 진입한다. 등록 즉시 잔여원금 전액이 청구 대상이 되고, 미래 회차 스케줄은 청구 중지된다.
  다만 **청구중지 ≠ 연체**다. 미도래 원금에는 약정이자만 붙고 연체가산이자는 붙지 않는다(개인채무자보호법).
- **상각**은 대손상각 등록으로만 진입한다. 진입 전 상태는 연체 또는 해지여야 한다 (정상 채권 상각 불가).
- **상각 → 종료**: 상각 후 회수가 발생해 잔액이 0이 되면 종료. 회수액은 `상각채권추심이익`으로 인식한다.
- 종료·상각 채권은 연체 파생 판정 대상에서 제외한다.

### 3.3 유지 (수정 최소)

회계(전표·분개·재무상태표·손익계산서·일일자금일보·미지급·보증금), 은행내역 업로드·CODEF 계좌연동,
고객/기타거래처, 인증·권한·회사별 DB 멀티테넌시, 법적절차(`legal`), 내정보(계좌·법인카드), 구독·세무상담·이메일보고서.

> `legal` 모듈은 대부업 채권추심에서 오히려 핵심이므로 채권관리 메뉴로 이동시켜 강화한다.

### 3.4 재사용 가능한 자산 (중요)

**상환스케줄 계산 엔진이 이미 존재한다.** `vehicle/service/VehicleLoanScheduleAdjustService.java:150-215`에
원리금균등 / 원금균등 / 만기일시 3가지 방식의 회차별 원금·이자·잔여원금 계산이 구현되어 있다.
차량 구입 차입금(빌린 쪽)용이지만 계산식은 대출(빌려준 쪽)과 동일하므로 **`loan` 패키지로 추출해 재사용**한다.

단, 개선 필요 2건:
- 원리금균등에서 월납입액을 사용자 입력값(`loan.getMonthlyPayment()`)으로 받고 있다 → **PMT 공식 자동 산출로 교체**
  `PMT = P × r × (1+r)^n / ((1+r)^n − 1)`, `r = 연이율/12`
- 일할 정산 계산기가 없다 → 신규 작성

### 4.3 `AccelerationEvent` (기한이익상실) — 신규

| 필드 | 설명 |
|---|---|
| `contractNumber` | 채권번호 |
| `eodDate` | 기한이익상실일 |
| `reason` | 연체 / 파산·회생 / 신용악화 / 약정위반 / 기타 |
| `calledPrincipal` | 청구 원금 = 상실일 기준 잔여원금 전액 |
| `accruedInterest` | 상실일까지 미수이자 (**일할 정산**) |
| `accruedOverdue` | 상실일까지 지연배상금 |
| `noticeDate` | 통지일 (대부업법상 사전통지 의무) |
| `voucherId` | 연동 전표 |

등록 시 처리:
1. `LoanContract.status = '해지'`, **`repaymentMethod = '만기일시'`** (분할 상환이 끝났다)
2. 미도래 회차를 **`lineStatus = 일시청구` 1건으로 접는다**
   - 접은 회차들의 예정원금·기납입원금을 그대로 옮겨 미납원금이 변하지 않는다
   - 새 회차의 이자는 0 — 조기 상환된 구간의 약정이자는 발생하지 않았다
   - 이 원금에는 **지연배상금도 붙지 않는다** (개인채무자보호법)
   - 이미 납기일이 지난 미납 회차는 건드리지 않는다 (연체일수가 정확히 유지되어야 한다)
   - 취소 시: 상환방식을 원복하고 스케줄을 다시 만든 뒤 수납을 재계산(replay)해 복원한다
3. 상실일 기준 미수이자·지연배상금 일할 확정
4. 이후 지연배상금은 **원래 납기일이 도래한 미납 회차에만** 일할 기산한다.
   조기 변제기가 도래한 미도래 원금에는 **연체가산이자를 붙이지 않는다** (`overdueChargeYn = false`면 전부 미부과)

> ⚠️ **개인채무자보호법 (2026-08-29 반영)**
> 개인금융채권의 관리 및 개인금융채무자의 보호에 관한 법률상,
> **최초원금 5,000만원 미만 + 개인 채무자 + 개인금융채권** 세 조건을 모두 만족하면
> 기한이익상실이 나더라도 **원래 납기일이 도래하지 않은 원금에는 연체가산이자를 부과할 수 없다.**
>
> 이 문서의 이전 판은 "잔여원금 전액에 일할 기산"이라고 적혀 있었다. 그대로 구현하면 법 위반이다.
> 실제 코드는 청구중지 회차를 지연배상금 산정에서 제외하고 있어 결과적으로는 맞게 동작하고 있었지만,
> 근거가 '청구중지라서'였지 '미도래라서'가 아니었다. `LoanSettlementService.isDue()` 에 법적 근거를 명시하고,
> 계약에 `debtType`(개인금융채권/기타)을 추가해 판정 정보를 갖췄다.
>
> 판정과 계산 규칙은 `loan.policy.PersonalDebtorProtection` 과
> `loan.interest.PersonalLoanInterestCalculator` 에 모아 두었다.
> 연체이율은 정상이자를 포함한 최종 이율이다 — 약정 18%면 연체는 20%이지 38%가 아니다.

5. 상실 이후 들어온 상환은 **청구중지 회차의 원금도 차감**한다 (`AcceleratedRepaymentPolicy.REDUCE_PRINCIPAL`).
   '청구를 중지한다'와 '변제를 받지 않는다'는 다른 이야기다.
   기존 구현은 청구중지 회차를 변제충당에서 통째로 제외해, 잔여원금 전액을 청구해 놓고
   정작 그 원금을 갚을 수 없었다(입금이 전부 선수금으로 남았다).
   회사에 따라 상실 후 입금을 선수금으로 잡아 두는 실무도 있어 `HOLD_AS_PREPAID` 로 바꿀 수 있다.

### 4.4 `WriteOff` (대손상각) — 신규

| 필드 | 설명 |
|---|---|
| `contractNumber` | 채권번호 |
| `writeOffDate` | 상각일 |
| `reason` | 소멸시효완성 / 파산면책 / 회수불능 / 채권매각 / 기타 |
| `writeOffPrincipal` | 상각 원금 |
| `writeOffInterest` | 상각 미수이자 |
| `writeOffOverdue` | 상각 지연배상금 |
| `allowanceUsed` | 대손충당금 상계액 |
| `expenseAmount` | 대손상각비 계상액 |
| `voucherId` | 연동 전표 |

등록 시 처리:
1. `LoanContract.status = '상각'` (진입 전 상태는 연체 또는 해지여야 함)
2. 잔여채권 전액 제각, 이후 이자·지연배상금 기산 중단
3. 상각 후 회수 발생 시 `상각채권추심이익`으로 별도 인식

## 5. 계산 엔진

### 5.1 스케줄 생성 (월할)

```
monthlyRate = 연이율 / 100 / 12

원리금균등: PMT = P × r × (1+r)^n / ((1+r)^n − 1)
           회차이자 = 잔여원금 × r
           회차원금 = PMT − 회차이자

원금균등:   회차원금 = P / n
           회차이자 = 잔여원금 × r

만기일시:   회차원금 = (마지막 회차만 P, 나머지 0)
           회차이자 = 잔여원금 × r
```

- 납입예정일은 `startDate` 기준 `paymentDay`로 월별 생성, 말일 클램핑 (`withDaySafe` 로직 승계)
- 마지막 회차에서 단수 차이는 원금에 흡수 (기존 로직 승계)

### 5.2 정산 (일할)

중도상환 / 기한이익상실 / 완제 시점:

```
경과이자 = 잔여원금 × 연이율 / 100 / 365 × (정산일 − 직전납입일)
지연배상금 = 연체원금 × 연체이율 / 100 / 365 × 연체일수     (D+1 기산)
             ※ overdueChargeYn = false 이면 0
```

윤년도 365일 고정 (대부업 실무 관행). 원 단위 절사.

### 5.3 변제충당 (수납 시)

채권 상태에 따라 **두 가지 순서**를 적용한다.

#### (가) 일반 채권 — 정상 / 연체 / 해지

```
1) 법적비용    — 법적절차 비용, 추심비용 (legal 모듈 연동)
2) 이자        — 지연배상금 → 약정이자 순, 각 단계에서 오래된 회차 우선
3) 원금        — 잔여원금 차감
```

#### (나) 상각 채권 — `status = '상각'`

```
1) 법적비용
2) 원금        — 상각 원금 우선 회수
3) 이자        — 지연배상금 → 약정이자
```

> 상각채권은 회수 자체가 불확실하므로 원금을 먼저 회수해 회수율을 확보한다.
> 상각채권 회수액은 계정과목상 `상각채권추심이익`으로 인식하되, 원금/이자 내부 배분은 위 순서를 따른다.

**공통 규칙**
- 충당 결과는 `LoanSchedule.paidPrincipal / paidInterest / paidOverdueInterest`에 회차별로 기록해 부분납 상태를 추적한다.
- 잔액 발생 시 선수금 처리 (기존 선수금 로직 재사용).
- 충당 순서는 상수가 아니라 **전략(Strategy) 형태로 분리**해, 상태별 순서 교체와 향후 정책 변경을 코드 수정 없이 처리할 수 있게 한다.

> **확정**: '이자' 단계 내부에서는 **지연배상금을 약정이자보다 먼저** 충당한다.
> 지연배상금은 연체가 계속되는 동안 계속 불어나므로 먼저 끊어야 채무자 부담이 덜 늘어난다.

**법적비용의 범위 (확정)** — 변제충당 1순위 '법적비용'은 법적절차(`legal`) 모듈이 기록한 비용을 그대로 쓴다.

```
법적비용 총액 = Σ(신청비용 + 추가비용 + 확인비용) − Σ(환입)
미회수 법적비용 = 법적비용 총액 − Σ(스케줄 paid_cost)
```

- 신청비용·추가비용·확인비용은 채무자에게 청구할 비용, 환입은 법원 등에서 이미 돌려받은 금액이다.
- 법적절차가 없는 채권은 0이므로 1순위 단계를 그냥 지나간다.
- 충당 실적은 채권 단위라 회차로 나누지 않고 가장 오래된 회차의 `paid_cost`에 모아 기록한다.
  `paid_cost`는 회차 완납 판정(`dueTotal`/`paidTotal`)에 들어가지 않는다.
- 회수분은 전표에서 `법무비용` 대변(환입)으로 인식한다.

### 5.4 이율 상한 검증 (신규)

계약 등록·수정 시 서버단 검증:

```
interestRate ≤ MAX_RATE (기본 20.0)
overdueRate  ≤ min(interestRate + 3.0, MAX_RATE)
```

`MAX_RATE`는 법 개정 대비해 회사설정(`OtherAccountSettings` 또는 신규 설정 테이블)에서 관리하고
기본값 20.0으로 시딩한다. 화면단 검증만이 아니라 **서비스 레이어에서도 반드시 검증**한다.

### 손익계산서 — 영업이익 단계 추가

기존 손익계산서는 `수익 총계 − 비용 총계 = 당기순이익` 한 줄뿐이라 **영업이익 개념이 없었다.**
중분류 계정코드 기준으로 단계를 나눠 계산한다.

```
영업수익 (4001)
− 영업비용 (5001 이자비용·법무비용 + 5002 판매비와관리비)
──────────────────────────────
= 영업이익
+ 영업외수익 (4002)
− 영업외비용 (5003)
− 법인세 (5004)
──────────────────────────────
= 당기순이익
```

`IncomeStatementResponse`에 `operatingRevenue / operatingExpense / operatingIncome /
nonOperatingRevenue / nonOperatingExpense / incomeTax` 필드를 추가하고 손익계산서 화면에
'손익 단계' 섹션으로 표시한다.

**이자비용은 영업비용으로 확정**했다. 대부업은 자금 조달이 본업의 일부이므로 차입금 이자를 영업이익에 반영한다.
중분류 `5001 매출원가`를 `영업비용`으로 전환하고 그 아래 `500101 이자비용`·`500102 법무비용`을 두었다.

**법무비용도 영업비용으로 확정**했다. 채권추심 법적절차는 대부업 본업이고, 변제충당 1순위 `법적비용`이 바로 이 계정이다.

### 부가세 — 전면 삭제

**대부업 이자수익은 부가가치세 면세**(금융·보험 용역)이므로 부가세 처리를 시스템에서 완전히 제거한다.

제거 대상:
- 수납·중도해지·선수금·정기검사 전표의 **부가세예수금 10% 자동분리** (커밋 `4259313`, `3a1e623`)
- `payment.taxinvoice` 세금계산서 발행 모듈 및 화면
- `Contract.taxInvoiceDay` / `PaymentSchedule.taxInvoiceDate` 등 세금계산서 관련 필드
- 계정과목 중 `부가세예수금` / `부가세대급금` (매출·매입 모두 비활성화 — 확정)

> **확정**: **매입 부가세도 제외**한다. `부가세대급금`(100506)·`부가세예수금`(200103) 모두 비활성화하고
> 임차료·비품·용역 매입은 부가세를 분리하지 않고 **총액(공급대가)으로 비용 계상**한다.
> 실측한 209건 장부가 이미 그렇게 기표하고 있어 실무와도 일치한다.
> 면세사업자는 매입세액을 공제받지 못하므로 매입세액을 따로 잡을 실익이 없다.

### 대시보드 지표 (6단계)

대부업에서 매일 봐야 하는 숫자로 바꿨다.

| KPI | 계산 |
|---|---|
| 대출잔액 | 살아있는 채권의 잔여원금 합계 (상각·종료 제외) |
| 연체잔액 | 연체 + **해지(기한이익상실)** 채권의 잔여원금 |
| 연체율 | 연체잔액 ÷ 대출잔액 |
| 이번 달 회수율 | 당월 납입예정 회차의 수납액 ÷ 청구액 |
| 상각잔액 | 상각 채권 잔액 |

> 연체 지표에 기한이익상실 채권을 포함한다. 실질적으로 정상 회수가 막힌 채권이라
> 빼고 세면 연체율이 실제보다 좋아 보인다.

**연체 경과기간(Aging)** — 1~30 / 31~60 / 61~90 / 90일 초과.
한 채권에 연체 회차가 여러 개면 가장 오래된 회차로 구간을 정하고 금액은 합산한다
(회차 단위로 세면 건수가 부풀려진다). 90일 초과가 있으면 화면에 경고를 띄워
기한이익상실·대손상각 검토를 유도한다.

**상태 판정 규칙은 채권현황 화면과 동일**하게 맞췄다. 규칙이 갈리면 대시보드와
채권현황의 숫자가 어긋난다.

## 9. 결정 완료 (2026-08-24, 사장 결정)

미결 5건이 모두 확정됐다. 아래가 최종 결정이고, 본문(§1·§5.3·§6)에도 반영해 두었다.

| # | 사안 | 결정 | 반영 위치 |
|---|---|---|---|
| 1 | 매입 부가세 존치 여부 | **제외** — 매출·매입 모두 삭제. 매입도 총액으로 비용 계상 | §6, `seed_*`/`migrate_loan_business_accounts.sql` |
| 2 | 법적비용 항목 정의 | **변제충당 1순위에 포함** — 법적절차 모듈의 신청·추가·확인비용 합계 − 환입 | §5.3, `RepaymentPostingService` |
| 3 | 지연배상금 vs 약정이자 | **지연배상금 우선** | §5.3, `RepaymentAllocator` |

| 5 | 기한이익상실 자동 트리거 | **신청식(수동 등록)** — 자동 트리거 없음 | 기한이익상실 화면 안내 문구 |

### 결정별 구현 메모

**[1] 매입 부가세 제외**
계정과목은 이미 `부가세대급금`(100506)·`부가세예수금`(200103) 모두 비활성화 상태였다.
남아 있던 화면 쪽 잔재를 정리했다 — 청구 화면의 '세금계산서일자' 라벨을 '납기일'로,
'내정보관리 > 세금계산서 공급자 정보' 탭을 '사업자 정보'로 바꿨다. 청구서 양식에서 공급가액/세액 칸을
빼고 청구원금·청구이자·청구합계로 다시 짰다.
사업자등록번호·상호·주소 입력은 남긴다. 세금계산서용은 아니지만 대부업 등록·표시광고 의무 항목이다.

**[2] 법적비용 1순위 충당**
설계만 있고 실제로는 `outstandingCost = 0L` 이 하드코딩돼 1순위 단계가 항상 건너뛰어지고 있었다.
`LegalCostItemRepository.sumChargeableByContractNumber` 로 채권 단위 법적비용을 집계해
`RepaymentPostingService` 의 replay 루프에 흘려 넣도록 연결했다.
회수분은 전표에서 `법무비용` 대변(환입)으로 인식한다 — 이 전표 처리는 이미 구현돼 있었다.

**[3] 지연배상금 우선**
`RepaymentAllocator.ORDER_GENERAL` 이 이미 `COST → OVERDUE_INTEREST → INTEREST → PRINCIPAL` 이라
코드 변경 없이 확정만 하면 됐다. 상각채권은 `COST → PRINCIPAL → OVERDUE_INTEREST → INTEREST`.

**[4] 렌터카 테넌트 폐기**
코드상 두 계열은 이미 갈라져 있다. 대부업은 테넌트 DB 접두어 `loan_company_` + 템플릿 `loan_erp`,
렌터카는 `erp_company_*` + `erp` 를 썼고, `TenantDatabaseService.validateDbName` 이 항상
`loan_company_` 를 붙이므로 대부업 ERP가 렌터카 DB에 닿을 경로가 없다. 남은 건 치우는 일뿐이다.
`sql/discard_rentcar_tenants.sql` 에 절차를 담았다 — ①확인 조회 → ②계정 비활성화(되돌릴 수 있음)
→ ③계정 행 삭제 → ④`DROP DATABASE`(주석을 직접 풀어야 실행). 백업 없이 실행하지 말 것.

**[5] 기한이익상실 = 신청식**
자동 트리거는 넣지 않는다. 스케줄러는 월전표·만기종료·일일보고 3개뿐이고 어느 것도 기한이익상실을
건드리지 않는다. 담당자가 기한이익상실 화면에서 직접 등록해야 확정된다.
화면에 '자동 등록하지 않는다'는 안내와 연체현황 링크, 대부업법상 사전통지 의무(통지일 입력) 안내를 넣었다.
연체 90일 초과 채권은 대시보드 연체 경과기간에서 경고로 뜬다.
